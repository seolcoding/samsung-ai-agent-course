## 1-1 사전 학습과 Instruction Tuning (p3–5)

### 1-1 / [Q] 예측 (객관식) — 슬라이드를 보기 전에

**문제:** 사전 학습(Pre-training)만 거친 모델에 "To be or not to be"를 넣으면 무엇이 나올 가능성이 클까?(p4)

| 보기 | 정답 | 피드백 |
|---|---|---|
| ① "that is the question"처럼 문장을 이어 쓴다 | O | 사전 학습만 한 모델은 지시를 따르기보다 그럴듯한 글을 이어 쓰는 성향이 강하다(p4). |
| ② "이 문장은 햄릿의 대사입니다"라고 설명한다 | X | 설명하는 답은 지시 수행을 더 배운 모델의 모습이다(p5). |
| ③ "무엇을 도와드릴까요?"라고 되묻는다 | X | 되묻는 대화형 반응도 Instruction Tuning 이후에 강화되는 행동이다(p5). |

### 1-1 / [설명] p4

LLM은 먼저 아주 많은 글(웹 문서, 책, 코드, 대화)에서 문장이 이어지는 패턴을 배운다(p4).
이것을 사전 학습(Pre-training)이라고 한다(p4).
이 단계의 목표는 "지금까지 나온 글 다음에 올 가능성이 높은 토큰(글 조각)"을 맞히는 것이다(p4).
그래서 사전 학습만 한 모델은 "To be or not to be"를 받으면 질문으로 보지 않고 "that is the question"을 이어 쓴다(p4).

**왜 배우나:** 과정 첫 블록(1.1)은 LLM의 본질을 "다음 토큰 예측"으로 정리한다(CURRICULUM 1.1).
이 "다음 토큰 예측"은 바로 뒤 1-2에서 답이 토큰 하나씩 만들어지는 과정으로 이어진다(p4)(p6).

### 1-1 / [설명] p5

Instruction Tuning(지시 학습)은 모델이 사용자의 입력을 "해야 할 요청"으로 알아듣도록 추가로 가르치는 과정이다(p5).
질문과 답, 명령과 결과, 대화 예시 같은 데이터로 더 학습시킨다(p5).
슬라이드의 예시처럼 `instruction`(지시), `input`(입력), `output`(기대하는 답)을 한 묶음으로 보여 준다(p5).
우리가 API나 챗봇에서 쓰는 모델은 대체로 이 과정을 거친 모델이다(p5).
뒤에서 실행할 세 파일도 모두 "3문장으로 설명해줘"라는 지시를 보낸다(01_requests.py:33)(02_openai.py:38)(03_langchain.py:20).

**왜 배우나:** API 모델이 지시를 따르도록 조정된 모델이기 때문에, 지시를 어떻게 쓰느냐가 결과를 바꾼다(p5)(p16).
5절에서 CodeMate에게 일을 시키는 실습도 결국 "지시를 잘 쓰는 일"이다(outline 5절)(피드백 2.4).

### 1-1 / [정리]

사전 학습은 이어 쓰기를 배우고, Instruction Tuning은 지시 따르기를 배운다(p4)(p5).

## 1-2 다음 토큰 예측과 생성 과정 (p6–7)

### 1-2 / [설명] p6

LLM은 완성된 답을 한 번에 꺼내지 않는다(p6).
지금까지의 글을 보고 다음에 올 토큰들의 확률(가능성)을 계산한다(p6).
그중 하나를 골라 글 뒤에 붙이고, 이것을 반복한다(p6).
이 반복으로 단어, 문장, 문단, 최종 답이 차례로 만들어진다(p6).
뒤의 Streaming(스트리밍: 답을 다 만들기 전에 조각이 생기는 대로 받는 방식) 실행에서 이 "하나씩 붙는 모습"을 화면으로 본다(02_openai.py:62-72)(03_langchain.py:28-32).

**왜 배우나:** 답이 조각으로 만들어진다는 것을 알아야 스트리밍 응답을 이해할 수 있다(p6)(02_openai.py:62).
스트리밍은 뒤에서 RAG 체인과 Streamlit 챗봇 화면을 만들 때 다시 쓰인다(CURRICULUM 2.1)(CURRICULUM 2.3).

### 1-2 / [설명] p7

LLM API의 응답은 p6의 반복 생성을 서비스로 감싼 것이다(p7).
API(프로그램끼리 요청과 답을 주고받는 창구)는 다음 네 단계로 움직인다(p7).

1. 사용자가 메시지와 설정값을 요청으로 보낸다(p7).
2. 서버의 모델이 입력을 읽고 다음 토큰 후보를 계산한다(p7).
3. 고른 토큰이 쌓여 답 메시지가 된다(p7).
4. 끝낼 조건에 닿으면 최종 답을 응답으로 돌려준다(p7).

첫 실행 파일 `01_requests.py`에서 1단계(요청 보내기)와 4단계(응답 받기)가 코드 줄로 보인다(01_requests.py:45-54).
2·3단계는 서버 안에서 일어나서 코드에는 보이지 않는다(p7).

**왜 배우나:** 이 네 단계는 앞으로 모든 LLM 호출의 기본 모양이다(p7).
③에서 쓰는 LangChain의 `get_llm()`도 속에서는 게이트웨이 주소로 이 요청을 보낸다(llm.py:38-42).

### 1-2 / [Q] 순서 맞추기 — p7의 네 단계

**문제:** 섞인 네 단계를 API가 실제로 움직이는 순서로 놓으세요(p7).

| 화면에 섞어 보여 줄 카드 | 정답 순서 |
|---|---|
| 선택된 토큰들이 누적되어 응답 메시지가 만들어진다 | 3 |
| 사용자가 메시지와 설정값을 API 요청으로 보낸다 | 1 |
| 생성이 종료 조건에 도달하면 최종 답변이 API 응답으로 반환된다 | 4 |
| 서버의 모델이 입력 문맥을 읽고 다음 토큰 후보를 계산한다 | 2 |

**피드백(정답 후):** 요청 → 후보 계산 → 누적 → 반환 순서다(p7). 2와 3은 p6의 반복이 서버 안에서 일어나는 부분이다(p6)(p7).

### 1-2 / [정리]

모델은 토큰을 하나씩 골라 붙이고, API는 이 과정을 "요청 → 계산 → 누적 → 반환"으로 감싼다(p6)(p7).

이 단계도 화면에 찍는 것이 없으니, 위 코드 화면에서 30~43줄을 직접 본다(concepts ① 단계 2).

### ① 단계 3 / [볼 지점]

- 오류가 나면 `raise_for_status()`가 낸 메시지(상태 코드)를 먼저 본다(01_requests.py:48).

### ① / [정리]

## 2-1 토큰의 의미 (p8–9)

### 2-1 / [설명] p9

Tokenization은 사람의 말을 모델이 다룰 수 있는 작은 단위로 나누는 과정이다(p9).
나뉜 단위를 토큰이라고 부른다(p9).
토큰은 단어와 항상 같지 않고, 단어의 일부나 공백·기호·숫자 조각이 될 수 있다(p9).

예시에서 "를", "다", "." 같은 조각이 따로 떨어진 것을 보라(p9).
모델은 글자가 아니라 토큰마다 숫자 묶음(벡터)으로 바꾼 것을 입력받는다(p9).

**왜 배우나:** 입력 프롬프트와 모델의 답은 모두 토큰 단위로 센다(p9).

## 3-1 Context Window (p12–14)

### 3-1 / [설명] p14

Context Window는 모델이 한 번의 요청에서 읽고 고려할 수 있는 토큰 범위다(p13)(p14).
이 범위에는 시스템 메시지, 사용자 메시지, 이전 대화, 도구 실행 결과가 모두 들어간다(p14).
모델은 이번 요청에 들어 있지 않은 정보를 직접 볼 수 없다(p14).
그래서 긴 문서는 나누어 필요한 부분만 검색해 넣고, 긴 대화는 요약하거나 중요한 상태만 따로 저장한다(p14).
여러 도구를 쓰는 Agent는 다음 판단에 필요한 정보만 남겨야 한다(p14).

**왜 배우나:** 컨텍스트 윈도우는 LLM 애플리케이션 설계의 한계를 정한다(p14)(피드백 2.2).
모델은 매번 대화를 통째로 다시 읽고, 넘치면 앞부분을 잃어 할루시네이션이 생길 수 있으며, 길수록 매 턴 비용이 커진다(피드백 3.3).
그래서 요약(compaction), RAG(2.1), LangGraph의 state(상태) 설계(2.2)가 필요하다(피드백 3.3)(CURRICULUM 2.1)(CURRICULUM 2.2).

## 3-2 입력 품질과 출력 품질 (p15–16)

### 3-2 / [설명] p16

LLM의 답 품질은 모델 성능만이 아니라 컨텍스트에 어떤 정보를 넣었는지에 크게 좌우된다(p15)(p16).
목표가 분명하면 답의 방향이 안정된다(p16).
배경 정보가 충분하면 추측과 환각(할루시네이션: 사실이 아닌 내용을 지어내는 것)이 줄어든다(p16).
쓸데없거나 서로 부딪히는 정보가 많으면 모델의 판단이 흐려질 수 있다(p16).
좋은 프롬프트(모델에게 주는 지시문)는 답을 맞히라고 요구하지 않고, 답을 만들 수 있는 조건을 준다(p16).

**왜 배우나:** 5절에서 CodeMate에게 줄 지시문을 이 틀로 쓴다(outline 5절).
코드 구조를 알고 분명하게 지시하면 뭉뚱그린 질문보다 결과가 좋다(피드백 2.4)(피드백 3.2).

### 3-2 / [체크] p16의 네 항목 (5절 지시문 틀)

- [ ] 역할과 목표를 분명히 준다(p16).
- [ ] 필요한 배경 정보와 제약 조건을 함께 준다(p16).
- [ ] 원하는 출력 형식과 평가 기준을 알려 준다(p16).
- [ ] 모호한 지시나 서로 부딪히는 요구를 줄인다(p16).

이 네 칸은 5절 CodeMate 지시문의 제목으로 그대로 다시 나온다(outline 5절).

### 3-2 / [정리]

좋은 입력은 역할·목표, 배경·제약, 출력 형식, 모호함 줄이기의 네 조건을 준다(p16).

## 4-1 System, User, Assistant 역할 (p17–18)

### 4-1 / [설명] p18

Chat 기반 LLM API는 대화를 역할이 붙은 메시지 목록으로 나타낸다(p18).
System 메시지는 모델의 전체 역할, 규칙, 제약 조건을 정한다(p18).
User 메시지는 사용자의 질문, 요청, 입력 데이터를 전한다(p18).
Assistant 메시지는 LLM이 만든 답이고, 다음 대화에 더해져 맥락을 전한다(p18).
역할 구분은 모양만이 아니라 모델이 지시의 우선순위와 대화 흐름을 읽는 기준이다(p18).

**왜 배우나:** 4일차 Harness 실습에서 "범위를 벗어난 요청 거절"을 system prompt로 만든다(CURRICULUM 4.1).
2-2에서 본 것처럼 시스템 메시지와 이전 대화도 매번 입력 토큰이 된다(p10).

### 4-1 / [되돌아보기] ② 단계 3의 코드 화면 (재실행 없음)

- 02는 System 대신 `developer`라는 이름을 쓴다(02_openai.py:48). 주석이 "시스템 지시"라고 설명한다(02_openai.py:46)(02_openai.py:48)(outline 어긋남 1).
- 01은 `user` 메시지 하나만 보낸다(01_requests.py:33)(outline 어긋남 1).
- 02의 Assistant 메시지는 `response_1.output`을 통째로 이어 붙여서 코드 화면에 글자로 보이지 않는다(02_openai.py:55)(outline 어긋남 2).
- 그래도 두 번째 답이 "그곳"을 알아들었다면, Assistant 메시지가 맥락을 전한 것이다(p18)(02_openai.py:55-58).

### ③ 단계 3 / [설명] Streaming (27~32줄) — 실행 전에 읽는다

**실행 전 안내: 출력이 길다(03_langchain.py:32). 각 줄의 `content=` 뒤 글자만 보라(concepts ③ 단계 3).**
`stream()`은 답을 조각으로 하나씩 돌려준다(03_langchain.py:28)(03_langchain.py:31).
주석은 `end=''`로 줄바꿈 없이 출력한다고 적었지만, 원본 코드는 `print(chunk)`로 조각 객체를 통째로 한 줄씩 찍는다(03_langchain.py:29)(03_langchain.py:32)(outline 어긋남 5).
그래서 한 줄에 글자 말고도 여러 정보가 함께 보인다(03_langchain.py:32).

**왜 배우나:** 조각이 한 줄씩 쌓이는 모습이 p6의 "토큰을 하나씩 붙인다"를 보여 준다(p6).
정답본은 `chunk.content`만 찍는다(sol 03_langchain.py:27). 두 방식의 차이는 5절 실습 B에서 CodeMate와 비교한다(outline 5절 B).

### ③ 단계 3 / [볼 지점]

- 각 줄의 `content=` 뒤 글자가 조각으로 이어지는지 본다(p6)(03_langchain.py:32).
- 마지막 조각 근처에 `usage_metadata`가 있으면 입력·출력 토큰 수를 출력에서 직접 읽는다(p10)(outline 원칙).
- 없으면 "이 환경에서는 제공되지 않음"으로 적는다(outline 원칙). 03에는 `stream_usage` 설정이 없어 마지막 조각에 없을 수 있다(outline 어긋남 7).
- 조각 줄 수는 토큰 수와 같지 않다(outline 어긋남 6).

### ③ / [정리]

`get_llm()`이 모델 준비를 하나로 모았고, `invoke`는 한 번에, `stream`은 조각으로 받는다(llm.py:14-51)(03_langchain.py:24)(03_langchain.py:31).

## 4-2 모델 파라미터의 영향 (p19)

### 4-2 / [설명] p19

모델 파라미터(모델에 함께 넘기는 설정값)는 같은 입력에서도 답이 얼마나 다양하고 길고 예측 가능할지를 조정한다(p19).
Temperature는 다음에 올 수 있는 토큰들의 확률을 조정한다(p19).
Top-p는 후보 토큰들의 누적 확률 한도를 조정한다(p19).
낮은 값은 일관되고 보수적인 답에, 높은 값은 다양한 표현과 아이디어에 유리하다(p19).
너무 높으면 전혀 가능성 없는 토큰이 나올 수 있어 조심한다(p19).

**왜 배우나:** p6에서 모델이 "후보 중 하나를 고른다"고 했는데, 그 고르는 방식을 사람이 조정하는 손잡이가 이 두 값이다(p6)(p19).
같은 코드를 다시 실행해도 답이 조금씩 다를 수 있는 이유이기도 해서, 이 교안은 실행 출력을 정답으로 고정하지 않는다(p19)(outline 원칙).

### 4-2 / [지도] 01과 02의 파라미터 위치 (실행 안 함)

- 01은 `"temperature": 0.5`를 보낸다(01_requests.py:35).
- 모델이 `gpt-6-luna`일 때만 `temperature`를 뺀다(01_requests.py:40-42).
- 사내 경로에서는 0.5가 그대로 전송된다(01_requests.py:38-39)(outline 어긋남 3).
- 02 끝의 `temperature=0.2`, `top_p=0.1` 예시는 따옴표(docstring) 안에 있어 실행되지 않는다(02_openai.py:81-89)(outline 어긋남 3).
- 02의 주석은 "temperature와 top_p를 동시에 조정하는 것은 권장하지 않음"이라고 적었다(02_openai.py:79).

### 4-2 / [Q] 객관식

**문제:** p19 표에서 코드 생성에 맞는 조합은?(p19)

| 보기 | 정답 | 피드백 |
|---|---|---|
| ① 낮은 temperature / 낮은 top-p | O | 보수적이고 반복 가능성이 높아 사실 기반 답변, 코드 생성, 요약에 맞다(p19). |
| ② 낮은 temperature / 높은 top-p | X | 업무 문서, 설명문에 맞는 조합이다(p19). |
| ③ 높은 temperature / 낮은 top-p | X | 가벼운 문장 변형에 맞는 조합이다(p19). |
| ④ 높은 temperature / 높은 top-p | X | 아이디어 발산, 브레인스토밍에 맞는 조합이다(p19). |

### 4-2 / [정리]

Temperature와 Top-p를 낮추면 일관된 답, 높이면 다양한 답이 나온다(p19).

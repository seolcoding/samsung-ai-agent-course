A스킬을 단계적으로 여는 원리

강사 메모

Agent는 시작할 때 스킬마다 이름과 설명(SKILL.md 맨 위 --- 사이)만 시스템 프롬프트로 받습니다. 요청이 그 설명과 맞는다고 판단하면 그때 read_file로 SKILL.md 전체를 엽니다. 이것을 progressive disclosure(단계적 공개)라고 부릅니다. 그래서 설명 한 줄이 "열지 말지"를 정합니다.

Bcreate_deep_agent란 무엇인가

강사 메모

create_deep_agent는 안에서 2일차의 create_agent를 그대로 부르고, 그 둘레에 장비를 미리 얹습니다: 스킬 목록, 파일 도구 7개, 하위 Agent에게 맡기는 task 도구, 길어진 대화 줄이기. LAB 3.2 Agent의 도구는 9개(파일 7 + task + 우리가 준 search_web)입니다. 계획 도구 write_todos는 0.7부터 기본이 아니라 우리 0.7.18에는 없습니다.

이렇게 말해요

"2일차에 create_agent로 '모델이 도구를 부르고, 결과를 보고, 다시 판단하는' 반복을 만들었죠. create_deep_agent는 그 반복은 그대로 두고, 일하는 데 필요한 장비를 미리 챙겨 주는 함수입니다. 빈 책상이 아니라 서랍(파일 도구), 매뉴얼 목차(스킬), 동료를 부르는 전화(task)까지 갖춘 책상에 앉히는 거예요. 그래서 우리가 준 적 없는 read_file이 출력에 나옵니다. 이렇게 모델 둘레에 일할 환경을 만들어 주는 것을 하네스라고 부릅니다."

강사 메모

D하네스 5단계 중 검증·예외 처리는 실습 어디에

강사 메모

검증은 오늘 사람이 눈으로 합니다: 답이 [DS-AI-RPT v2.1]로 시작하는지, 도구 결과에 @@ lines 줄이 있는지. 예외 처리는 두 가지입니다: 범위 밖 요청은 시스템 프롬프트로 거절, 끝나지 않는 반복은 recursion_limit 40에서 오류로 멈춤. create_deep_agent의 기본 상한은 9,999라 40을 주지 않으면 사실상 상한이 없습니다. 항상 도구만 부르는 가짜 모델로 돌려 보니 모델을 19번 부른 뒤 GraphRecursionError로 멈췄습니다.

이렇게 말해요

"하네스를 설계하는 다섯 단계 중 마지막 두 개가 검증과 예외 처리입니다. 오늘 실습의 검증은 여러분 눈이에요. 답이 [DS-AI-RPT v2.1]로 시작하는지, 도구 결과에 @@ lines 줄이 있는지 보면 됩니다. 예외 처리는 두 가지입니다. 범위 밖 요청은 시스템 프롬프트로 거절하게 했고, Agent가 끝없이 돌면 40번째 단계에서 오류를 내고 멈추게 했어요. 자동차로 치면 브레이크를 미리 달아 둔 셈입니다. 눈으로 하던 검증을 코드와 LLM이 점수로 매기게 하는 건 다음 시간 4-2에서 합니다."

화면에서 짚을 것

  • LAB 2.1 볼 지점헤더 [DS-AI-RPT v2.1]로 스킬을 따랐는지 확인한다는 문장.
  • LAB 3.2system_prompt의 거절 문장(사례 2 퀵소트).
  • LAB 3.3chat() 안의 "recursion_limit": 40 줄과 그 위 주석(기본값 9,999라 40으로 낮춘다).

40은 어떻게 정한 숫자인가요?

네. interrupt_on으로 특정 도구를 부르기 직전에 멈추게 할 수 있습니다. 오늘 기본 실습에는 없고, 보강 실습에서 해 봅니다.

이렇게 말해요

Langfuse, Observability & Application Tracing

"The core of this is application tracing — structured logs of every request that capture the exact prompt sent, the model's response, token usage, latency, and any tools or retrieval steps in between."

핵심은 요청마다 남기는 구조화된 기록이다. 실제로 보낸 프롬프트, 모델의 답, 토큰, 걸린 시간, 중간의 도구·검색 단계가 담긴다.

같은 문서

Ftrace · observation · span · generation · score

강사 메모

trace = 요청 하나의 전체 기록. observation = 그 안의 한 단계(트리의 한 줄). span = 걸린 시간을 재는 일반 단계(@observe를 붙인 함수가 기본으로 이것). generation = 모델 호출 단계(프롬프트·토큰·비용이 붙음). score = 평가 결과(이름과 값). Langfuse 문서도 span을 넓게는 "단계 전체", 좁게는 "한 종류"로 둘 다 씁니다.

이렇게 말해요

"trace는 요청 하나에 대한 영수증이라고 생각하시면 됩니다. 영수증에는 줄이 여러 개 있죠. 그 줄 하나하나를 observation이라고 부릅니다. 그중 AI 모델을 부른 줄은 generation이라고 하고, 여기에 토큰과 비용이 적힙니다. 걸린 시간만 적힌 일반 줄은 span이고요. 마지막으로 score는 이 영수증에 붙이는 '잘했다, 못했다' 평가 스티커입니다."

화면에서 짚을 것
  • LEC 1.3 · p6Trace 슬라이드에서 영수증 비유를 꺼냅니다.
  • LEC 1.5 · p8@observe가 "Trace 또는 Span"을 만든다는 문장 → 아래 질문 답으로 정리.
  • LAB 3장trace 트리를 열고 아래 모양을 위에서부터 짚습니다. ChatOpenAI 줄을 눌러 토큰을 보여 줍니다.

질문이 나오면
슬라이드에는 @observe가 Trace 또는 Span을 만든다는데, 어느 쪽인가요?
Langfuse도 span을 두 뜻으로 씁니다. 넓게는 trace 안의 단계 전체, 좁게는 시간을 재는 한 종류입니다. @observe를 붙인 함수는 트리에 span 한 줄로 들어갑니다.
토큰과 비용은 어디서 보나요?
모델을 부른 줄, generation 줄을 누르면 보입니다.

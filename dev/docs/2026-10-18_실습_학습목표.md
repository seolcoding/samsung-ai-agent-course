# 실습 학습 목표와 과제 구조 (2026-10-18 확정)

14차수부터 쓰는 실습 과제의 기준이다. 실습마다 학습 목표를 정하고, 과제는 **그 목표를 코드로 구현할 수 있는지** 확인한다. 목표 하나가 채점 기준 하나다.
목표는 교안 PDF와 원본 실습 코드를 실습마다 조사해 후보를 만들고(서브에이전트 병렬 조사), 강사가 실습별로 골랐다.

## 1. 구조

| | M1 (1·2일차) | M2 (3·4일차) |
|---|---|---|
| 방식 | **챗봇 트랙**: 장을 배울 때마다 같은 챗봇을 한 단계씩 키운다 | **실습별 독립 과제**: 챗봇과 다른 터미널 프로그램, 한 파일·한 명령 |
| 위치 | `course/Chapter01/chatbot/` (화면 `ui.py`는 고정, 단계 파일 `stageN.py`) + 터미널 과제 `course/Chapter01/tasks/<번호>/` | `course/Chapter02/tasks/<번호>/` |
| 실행 | `uv run --env-file .env streamlit run course/Chapter01/chatbot/stageN.py` | `uv run --env-file .env python course/Chapter02/tasks/<번호>/task.py` |
| 채점 | AI에게 "N단계 채점해 줘"(AppTest로 화면 없이 확인) | AI에게 "<번호> 과제 채점해 줘" |

공통 결정:
- 실습 노트북은 객관식판 하나로 통일하고 이름을 `_LAB`으로 바꾼다. 옛 빈칸판은 빌드하지 않는다(git 이력에 남음).
- 과제 파일은 노트북에서 만들지 않는다. 시작 파일과 안내(README: 목표, 할 일, 프롬프트 힌트, 실행 명령, 채점받는 법)를 폴더에 미리 둔다.
- 프롬프트는 힌트만 준다(지시문 완성본은 주지 않는다). 채점은 AI(`grade-task` 스킬)만 한다.
- 챗봇 단계 파일의 시작본 = 직전 단계 완성본 + 이번 단계 빈 자리. 놓친 사람도 그 단계부터 시작할 수 있다. 화면(`ui.py`)은 Streamlit 템플릿으로 주고, 단계마다 `answer()` 함수만 바꾼다. Streamlit 자체는 2-3에서 `ui.py`를 처음 열어 본다.
- 2-2 Multi-Agent는 Streamlit에 억지로 넣지 않고 터미널 과제로 한다(시연 위주, 고객사 약속).

## 2. 실습별 학습 목표

### M1 — 챗봇 트랙

| 실습 | 형태 | 학습 목표 |
|---|---|---|
| **1-2 LLM API** | 터미널 + 챗봇 1단계 | ① `requests`로 HTTP 요청을 직접 보내 LLM 답(`choices[0].message.content`)을 꺼낼 수 있다(터미널) ② SDK(`chat.completions.create`)로 system·user 메시지를 보내 답을 받을 수 있다(터미널) ③ LangChain(`get_llm()`)으로 호출하고 `stream()`으로 답을 조각 단위로 화면에 보여 줄 수 있다(챗봇) ④ system·user를 나눈 `ChatPromptTemplate`에 변수를 넣어 호출할 수 있다(챗봇) |
| **1-3 LangChain** | 챗봇 2단계 | ① `prompt \| llm \| StrOutputParser()` LCEL 체인으로 답할 수 있다 ② `MessagesPlaceholder("history")`에 이전 대화를 넣어 앞의 말을 기억하게 할 수 있다 ③ `@tool`을 `bind_tools`로 연결하고 `tool_calls`를 실행해 `ToolMessage`로 돌려 최종 답을 받을 수 있다 ④ Pydantic 스키마로 답을 정해진 모양으로 받아 보여 줄 수 있다 |
| **1-4 RAG** | 챗봇 3단계 | ① PDF 읽기·분할·`get_embeddings()`·Chroma 저장을 `@st.cache_resource`로 한 번만 만들 수 있다 ② `as_retriever(k=3)`로 찾은 청크를 context로 넣어 답하고 근거를 보여 줄 수 있다 ③ 맥락에 없는 질문에는 "문서에서 확인할 수 없습니다"라고 답하게 할 수 있다 ④ 검색 방식(로컬 Chroma / 사내 RAGaaS)을 골라 두 검색 결과를 비교할 수 있다(**사내망**, 사외는 mock) |
| **2-1 LangGraph** | 챗봇 4단계 | ① `StateGraph`에 agent 노드와 `ToolNode`를 넣고 `Literal` 반환 갈림길 함수로 conditional edge를 이어 compile할 수 있다 ② 약관 검색을 `@tool search_policy`로 바꿔 약관 질문에서만 tools 노드를 거치게 할 수 있다 ③ `MemorySaver`와 `thread_id`로 대화 기억을 그래프에 맡길 수 있다 ④ `interrupt`로 도구 실행 전에 멈추고 승인·거부로 재개할 수 있다 |
| **2-2 Multi-Agent** | 터미널 과제 | ① Researcher와 Writer 노드를 만들고 `research_result`·`draft` 키로 결과를 넘길 수 있다 ② Researcher에게만 검색 도구를 줘 `Tool Message`가 Researcher 단계에만 나오게 할 수 있다 ③ Supervisor가 구조화 출력(`Literal['researcher','writer','FINISH']`)으로 다음 차례를 고르고 그 흐름을 출력할 수 있다 ④ Reviewer가 "통과/수정"을 내고 수정이면 최대 N번만 다시 쓰고 멈추게 할 수 있다 |
| **2-3 Streamlit** | 챗봇 5단계(마무리) | ① 일반 질문·약관 질문·기억 질문이 한 화면에서 모두 동작하는 최종 챗봇을 완성할 수 있다 |

### M2 — 실습별 독립 과제

| 실습 | 학습 목표 |
|---|---|
| **3-1 복습** | ① `config.check`로 설정을 점검하고 ⛔ 항목을 고쳐 모델 호출까지 통과시킬 수 있다 ② `get_embeddings()`와 Chroma로 검색기를 만들고 `@tool search_policy`로 감쌀 수 있다 ③ `tools_condition`과 `add_edge("tools","agent")`로 도구를 반복해 부르는 그래프를 만들 수 있다 ④ 약관 질문에서만 도구를 부르고 인사에는 부르지 않는 것을 `pretty_print`로 보여 줄 수 있다 |
| **3-2 MCP** | ① FastMCP `@mcp.tool()`로 함수 2개를 MCP 도구로 등록할 수 있다 ② `MultiServerMCPClient`를 stdio로 연결해 `get_tools()`로 도구 목록을 받을 수 있다 ③ 받은 MCP 도구를 LangGraph Agent에 붙여 질문에 도구로 답하게 할 수 있다 ④ `@mcp.resource()`와 `@mcp.prompt()`를 정의하고 읽어 올 수 있다 |
| **3-3 A2A** | ① `t.AgentCard`와 `t.AgentSkill`로 Agent Card를 만들 수 있다 ② `AgentExecutor`에서 Agent 결과를 `t.Message`로 `EventQueue`에 내보내는 서버를 Starlette 앱으로 조립할 수 있다 ③ `A2ACardResolver`로 카드를 읽고 메시지를 보내 응답 텍스트를 출력할 수 있다 |
| **3-4 LangGraph 심화** | ① 따로 compile한 서브그래프를 부모 노드에서 호출해 결과를 부모 State로 넘길 수 있다 ② fan-out/fan-in으로 두 작업을 동시에 실행하고 `Annotated` 리듀서로 모을 수 있다 ③ `MemorySaver`와 `thread_id`로 같은 thread는 이어 가고 다른 thread는 모르는 것을 `get_state` 메시지 수로 보일 수 있다 ④ `InMemoryStore` namespace에 사용자 정보를 `put`하고 새 thread에서 `search`로 꺼내 쓸 수 있다 |
| **4-1 Harness** | ① `@tool` 도구와 시스템 프롬프트를 `create_deep_agent`에 묶어 Agent를 만들 수 있다 ② 머리말(`name`·`description`)과 양식 본문이 있는 SKILL.md를 쓰고 skills 폴더로 연결해 그 양식대로 답하게 할 수 있다 ③ `system_prompt`로 범위 밖 요청을 거절시키고 두 요청의 결과를 비교할 수 있다 ④ 코드·모델은 그대로 두고 SKILL.md 한 줄만 바꿔 출력이 달라지는 것을 전후 비교로 보일 수 있다 |
| **4-2 관측** | ① `CallbackHandler`를 config로 넘겨 체인 실행을 trace로 기록하고 trace ID를 출력할 수 있다 ② `@observe(name=...)`로 일반 함수를 한 trace 아래 중첩 span으로 기록할 수 있다 ③ 규칙 점수와 LLM 채점 점수(0~1)를 `create_score`로 남기고 `flush()`할 수 있다 ④ LangGraph 그래프에 `CallbackHandler`를 붙여 노드별 실행을 trace로 기록할 수 있다 |

## 3. 확인 방법의 원칙

- 모델 답은 실행마다 달라진다. 답이 하나로 정해지는 질문(곱셈, 이름 기억)과 구조(메시지 칸, 노드 순서, 청크 수, 도구 이름)와 코드로 판정한다.
- 명령 한 번으로 끝나야 한다. 서버가 필요한 실습은 과제 파일이 잠깐 띄우고 끈다(3-2 stdio, 3-3 빈 포트).
- 챗봇은 `streamlit.testing.v1.AppTest`로 화면 없이 확인한다. 단계별 질문은 채점 기준 파일에 적는다.
- 사내망 전용(RAGaaS, 사내 게이트웨이의 도구 호출·구조화 출력, 강의장 Langfuse)은 사외에서 ❔(확인 불가)로 처리하고 사내 점검 때 확인한다. 사내 게이트웨이의 `bind_tools`는 1일차 점심 점검에 넣는다.

## 4. 근거

- 1차 목표 조사(실습별 12개): 실습마다 교안 PDF·원본 코드·노트북 spec을 읽은 서브에이전트 결과.
- 챗봇 트랙 설계: `dev/demos/rag_evolution/`(강사 데모 앱, 단계 순서 1 날것 API → 2 템플릿 → 3 LCEL·기억 → 4 Tool → 5 LangGraph → 6 RAG …)과 14차수 고객사 조정안(챗봇 실습 확대, 1·2일차 1시간씩, Streamlit은 챗봇에 통합, Multi-Agent·LangGraph 축소, RAGaaS 확대).
- M2 독립 과제 결정: MCP·A2A 서버와 Streamlit 재실행이 맞지 않고, 4-3 캡스톤이 터미널 리서치 시스템이라 챗봇과 이어지지 않는다. 대신 MCP 도구·체크포인터·SKILL.md·Langfuse 점수가 캡스톤으로 이어진다.

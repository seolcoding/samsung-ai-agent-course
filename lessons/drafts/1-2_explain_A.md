## 1-1 사전 학습과 Instruction Tuning (p3–5)

### 1-1 / [Q] 예측 (객관식)
- 질문: 사전 학습만 거친 모델에 "To be or not to be"를 넣으면 무엇이 나올까요? (p4)
- 보기
  1. that is the question ← 정답
  2. "이 문장은 셰익스피어의 햄릿에 나오는 대사입니다."
  3. "무엇을 도와드릴까요?"
- 정답 풀이: 사전 학습만 거친 모델은 그럴듯한 텍스트를 이어 씁니다. 그래서 문장의 다음 부분이 나옵니다 (p4).
- 오답 풀이
  - 2번: 문장을 설명하는 것은 요청으로 해석한 답입니다. 그렇게 만드는 과정은 다음 쪽의 Instruction Tuning입니다 (p5).
  - 3번: 사전 학습만 거친 모델은 지시를 따르기보다 이어 쓰는 성향이 강합니다 (p4).

### 1-1 / [설명] p4
LLM은 먼저 많은 글에서 말의 패턴을 배웁니다. 그다음 사람의 지시에 답하도록 더 조정됩니다 (p4).
사전 학습(Pre-training)은 웹 문서, 책, 코드, 대화 같은 많은 글에서 문장 사이의 통계적 패턴을 배우는 단계입니다 (p4).
이 단계의 목표는 앞 문맥 다음에 올 가능성이 높은 토큰을 맞히는 것입니다 (p4).
그래서 사전 학습만 거친 모델은 지시를 따르기보다 그럴듯한 글을 이어 쓰는 성향이 강합니다 (p4).
"To be or not to be"를 넣으면 "that is the question"이 이어 나옵니다 (p4).

### 1-1 / [설명] p5
Instruction Tuning(지시 학습)은 요청을 이해하고 답변 형식으로 응답하도록 모델의 행동을 조정하는 과정입니다 (p5).
질문과 답변, 명령과 수행 결과, 대화 예시 같은 데이터로 모델을 더 학습시킵니다 (p5).
그러면 모델은 입력을 문장 조각이 아니라 해야 할 요청으로 해석합니다 (p5).
예시 데이터는 instruction(지시), input(입력), output(원하는 출력) 세 칸으로 되어 있습니다 (p5).
우리가 API나 챗봇에서 쓰는 모델은 대체로 사전 학습 뒤에 지시 수행 능력을 강화한 모델입니다 (p5).

### 1-1 / [정리]
사전 학습만 한 모델은 그럴듯하게 이어 쓰고, API로 쓰는 모델은 대체로 지시 수행을 강화한 모델입니다 (p4, p5).

## 1-2 다음 토큰 예측과 생성 과정 (p6–7)

### 1-2 / [설명] p6
LLM은 완성된 답을 한 번에 꺼내지 않습니다. 토큰을 하나씩 예측하며 문장을 만들어 갑니다 (p6).
모델은 지금까지의 문맥을 보고, 다음에 올 수 있는 토큰들의 확률 분포(후보마다 나올 가능성)를 계산합니다 (p6).
그중 토큰 하나를 고르고, 고른 토큰을 문맥 뒤에 다시 붙입니다 (p6).
이것을 되풀이하면 단어, 문장, 문단, 최종 답변이 차례로 만들어집니다 (p6).

### 1-2 / [설명] p7
LLM API의 응답은 이 반복 생성 과정을 서비스 형태로 감싼 결과입니다 (p7).
과정은 네 단계입니다 (p7).
1. 사용자가 메시지와 설정값을 API 요청으로 보냅니다 (p7).
2. 서버의 모델이 입력 문맥을 읽고 다음 토큰 후보를 계산합니다 (p7).
3. 선택된 토큰들이 쌓여 응답 메시지가 만들어집니다 (p7).
4. 생성이 종료 조건에 닿으면 최종 답변이 API 응답으로 돌아옵니다 (p7).

### 1-2 / [Q] 순서 맞추기
- 질문: 요청부터 응답까지 네 단계를 순서대로 놓으세요 (p7).
- 섞어서 보여 줄 카드
  - 선택된 토큰들이 누적되어 응답 메시지가 만들어진다.
  - 사용자가 메시지와 설정값을 API 요청으로 보낸다.
  - 생성이 종료 조건에 도달하면 최종 답변이 API 응답으로 반환된다.
  - 서버의 모델이 입력 문맥을 읽고 다음 토큰 후보를 계산한다.
- 정답 순서: 요청 보내기 → 후보 계산 → 토큰 누적 → 종료 후 반환 (p7).
- 피드백: 후보를 계산하고 고른 토큰을 붙이는 일이 반복되어야 답이 쌓입니다 (p6).

### 1-2 / [정리]
모델은 토큰을 하나씩 예측해 붙이고, API는 요청 → 후보 계산 → 누적 → 종료 후 반환의 순서로 답을 돌려줍니다 (p6, p7).

## 2-1 토큰의 의미 (p8–9)

### 2-1 / [설명] p9
Tokenization은 사람의 말을 모델이 처리할 수 있는 작은 단위로 나누는 과정입니다 (p9).
이렇게 나뉜 단위를 토큰이라고 부릅니다 (p9).
토큰은 단어 하나와 늘 같지 않습니다. 단어의 일부, 공백, 기호, 숫자 조각이 될 수 있습니다 (p9).
한국어는 조사와 어미, 띄어쓰기 특성 때문에 더 잘게 나뉠 수 있습니다 (p9).
모델은 원래 글자를 그대로 받지 않고, 토큰에 의미를 부여한 벡터(숫자 묶음)로 받습니다 (p9).
입력 프롬프트와 모델이 만드는 답변도 토큰 단위로 계산합니다 (p9).

## 2-2 토큰 수와 비용 (p10–11)

### 2-2 / [설명] p10
LLM API의 비용과 처리량은 보통 입력 토큰 수와 출력 토큰 수로 정해집니다 (p10).
LLM이 답하는 데 쓰는 모든 것이 입력 토큰에 들어갑니다. 입력 프롬프트, 시스템 프롬프트, 이전 대화 내용 등이 그렇습니다 (p10).
출력 토큰은 모델이 새로 만든 답변의 길이입니다 (p10).
생각하는 과정이 있는 모델은 생각하며 만든 토큰도 출력 토큰에 들어갑니다 (p10).
프롬프트와 답변이 길수록 비용이 늘고 응답 시간도 길어집니다 (p10).

### 2-2 / [되돌아보기] 실행 ①의 usage (공통)
실행 ①의 출력으로 돌아갑니다. 다시 실행하지 않습니다 (1-2_concepts.md 2-2).
"### 응답 Json" 아래 `usage`에서 입력 토큰 수와 출력 토큰 수를 직접 읽어 적습니다 (01_requests.py:52, p10).
값이 없으면 "이 환경에서는 제공되지 않음"이라고 적습니다 (1-2_outline.md 어긋남 7).

### 2-2 / [설명] p11
토큰 수를 조절하면 비용을 아낄 수 있습니다 (p11).
필요한 정보만 골라서 넣습니다 (p11).
되풀이되는 지시문과 대화 기록을 줄여서 넣습니다 (p11).
검색한 문서를 모두 넣지 않고 관련이 높은 일부만 넣습니다 (p11).
답변의 형식과 길이를 분명히 정해 필요 없는 출력을 줄입니다 (p11).

### 2-2 / [Q] 객관식
- 질문: 다음 중 입력 토큰 수에 들어가지 않는 것은? (p10)
- 보기
  1. 시스템 프롬프트
  2. 이전 대화 내용
  3. 모델이 새로 생성한 답변 ← 정답
  4. 사용자가 보낸 입력 프롬프트
- 정답 풀이: 모델이 새로 만든 답변은 출력 토큰입니다 (p10).
- 오답 풀이(1·2·4번 공통): LLM이 답하는 데 쓰는 모든 것이 입력 토큰에 들어갑니다. 시스템 프롬프트와 이전 대화도 마찬가지입니다 (p10).

### 2-2 / [정리]

### 3-1 / [설명] p14

## 4-2 모델 파라미터의 영향 (p19)

### 4-2 / [설명] p19
모델 파라미터는 같은 입력에 대해 답이 얼마나 다양하고, 길고, 예측 가능할지를 조정합니다 (p19).
Temperature(온도)는 다음에 나올 수 있는 토큰의 확률을 조정합니다 (p19).
Top-p(탑피)는 나올 수 있는 토큰들의 누적 확률 한도를 조정합니다 (p19).
값이 낮으면 일관되고 보수적인 답에 유리합니다 (p19).
값이 높으면 다양한 표현과 아이디어를 만드는 데 유리합니다 (p19).
다만 너무 높으면 전혀 가능성 없는 토큰이 나올 수 있으니 주의합니다 (p19).

| 설정 | 생성 경향 | 맞는 상황 |
|---|---|---|
| 낮은 temperature / 낮은 top-p | 보수적, 반복 가능성 높음 | 사실 기반 답변, 코드 생성, 요약 |
| 낮은 temperature / 높은 top-p | 방향은 안정, 표현 폭은 확보 | 업무 문서, 설명문 |
| 높은 temperature / 낮은 top-p | 제한된 후보 안에서 표현만 흔들림 | 가벼운 문장 변형 |
| 높은 temperature / 높은 top-p | 다양하고 예측하기 어려움 | 아이디어 발산, 브레인스토밍 |

(표 전체: p19)

### 4-2 / [지도 볼 지점] (공통)
01의 요청 본문에 `"temperature": 0.5`가 들어 있습니다 (01_requests.py:35).
`OPENAI_MODEL`이 `gpt-6-luna`일 때만 이 값을 뺍니다. 사내 경로에서는 0.5가 그대로 전송됩니다 (01_requests.py:38-43, 1-2_outline.md 어긋남 3).
02 끝의 temperature·top_p 예시는 `"""` 안에 있어 실행되지 않습니다 (02_openai.py:81-89).

### 4-2 / [Q] 객관식
- 질문: 코드 생성에 맞는 설정은? (p19)
- 보기
  1. 낮은 temperature / 낮은 top-p ← 정답
  2. 낮은 temperature / 높은 top-p
  3. 높은 temperature / 낮은 top-p
  4. 높은 temperature / 높은 top-p
- 정답 풀이: 보수적이고 반복 가능성이 높은 설정이라 사실 기반 답변, 코드 생성, 요약에 맞습니다 (p19).
- 오답 풀이
  - 2번: 업무 문서와 설명문에 맞는 설정입니다 (p19).
  - 3번: 가벼운 문장 변형에 맞는 설정입니다 (p19).
  - 4번: 아이디어 발산과 브레인스토밍에 맞는 설정입니다 (p19).

### 4-2 / [정리]
Temperature와 Top-p가 낮으면 일관된 답, 높으면 다양한 답에 유리하고, 너무 높으면 엉뚱한 토큰이 나올 수 있습니다 (p19).

## 6 정리 퀴즈 (객관식 4문항, 공통)

### 6 / Q1 LLM의 학습과 추론
- 질문: LLM이 답을 만드는 방식으로 맞는 것은? (p6)
- 보기
  1. 완성된 답을 한 번에 꺼낸다.
  2. 토큰을 하나씩 예측해 문맥 뒤에 붙이기를 반복한다. ← 정답
  3. 학습한 문서 중 가장 비슷한 문서를 그대로 돌려준다.
- 정답 피드백: 다음 토큰의 확률 분포를 계산해 하나를 고르고, 문맥 뒤에 붙이기를 되풀이합니다 (p6).
- 오답 피드백: LLM의 추론은 한 번에 완성된 답을 꺼내는 방식이 아닙니다 (p6).

### 6 / Q2 Tokenization
- 질문: 토큰에 대한 설명으로 맞지 않는 것은? (p9)
- 보기
  1. 토큰은 단어 하나와 항상 같다. ← 정답
  2. 단어의 일부, 공백, 기호, 숫자 조각이 토큰이 될 수 있다.
  3. 한국어는 조사와 어미 때문에 더 잘게 나뉠 수 있다.
  4. 입력 프롬프트와 모델의 답변 모두 토큰 단위로 계산한다.
- 정답 피드백: 토큰은 단어 하나와 항상 같지 않습니다 (p9).
- 오답 피드백(2·3·4번 공통): 이 보기는 p9에 적힌 설명 그대로입니다 (p9).

### 6 / Q3 Context Window
- 질문: Context Window에 대한 설명으로 맞는 것은? (p13, p14)
- 보기
  1. 모델이 학습한 전체 데이터의 크기다.
  2. 모델이 한 번의 요청에서 읽고 고려할 수 있는 토큰 범위다. ← 정답
  3. 모델이 지난 요청들을 저장해 두는 공간이다.
- 정답 피드백: 시스템 메시지, 사용자 메시지, 이전 대화, 도구 실행 결과가 모두 이 범위에 들어갑니다 (p13, p14).
- 오답 피드백: 모델은 현재 요청에 포함된 컨텍스트 밖의 정보를 직접 참조하지 못합니다 (p14).

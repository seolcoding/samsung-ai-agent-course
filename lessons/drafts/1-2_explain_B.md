## 1-1 사전 학습과 Instruction Tuning (p3–5)

### 1-1 / [Q] 예측 (객관식)

**질문**: 사전 학습만 거친 모델에 "To be or not to be"를 넣으면 무엇이 나올 가능성이 클까요? (p4)

| 보기 | 정답 | 피드백 |
|---|---|---|
| ① 이 문장이 셰익스피어 작품이라는 설명 | | 설명은 질문에 답하는 행동입니다(p5). 사전 학습만 한 모델은 그보다 이어 쓰기 성향이 강합니다(p4). |
| ② "that is the question"처럼 뒤를 이어 쓴 글 | ✔ | 맞습니다, p4의 예시 출력이 바로 이것입니다(p4). |
| ③ "무엇을 도와드릴까요?"라는 되묻기 | | 요청으로 알아듣고 응답하는 행동은 Instruction Tuning 뒤에 강해집니다(p5). |
| ④ 입력이 짧아서 오류가 난다 | | p4는 오류가 아니라 이어 쓰기를 보여 줍니다(p4). |

### 1-1 / [설명] p4

LLM은 먼저 아주 많은 글(웹 문서, 책, 코드, 대화)에서 말의 패턴을 배웁니다(p4). 이것을 사전 학습(Pre-training)이라고 합니다(p4).
이 단계의 목표는 "지금까지의 글 다음에 올 가능성이 높은 토큰(글의 작은 조각)"을 맞히는 것입니다(p4).
그래서 사전 학습만 한 모델은 지시를 따르기보다 그럴듯하게 이어 씁니다(p4).
"To be or not to be" 뒤에 "that is the question"이 붙는 예시가 그 모습입니다(p4).
"다음 토큰을 맞힌다"는 생각은 p6의 생성 과정에서 다시 나옵니다(p6).

### 1-1 / [설명] p5

Instruction Tuning(지시 따르기 조정)은 질문과 답, 명령과 수행 결과 같은 예시로 모델을 한 번 더 학습시키는 과정입니다(p5).
이렇게 하면 모델이 입력을 "이어 쓸 문장"이 아니라 "해야 할 요청"으로 읽게 됩니다(p5).
p5의 예시 데이터는 `instruction`(지시), `input`(입력), `output`(바라는 답) 세 칸으로 되어 있습니다(p5).
우리가 API나 챗봇으로 쓰는 모델은 대체로 이 과정을 거친 모델입니다(p5).
그래서 뒤의 실습 코드에서 "3문장으로 설명해줘"라고 지시만 적어도 답이 옵니다(p5, 01_requests.py:33).

### 1-1 / [정리]

사전 학습은 다음 토큰을 맞히며 이어 쓰기를 배우고, Instruction Tuning은 그 위에 요청에 답하는 행동을 더합니다(p4, p5).
실습에서 부르는 API 모델은 대체로 두 과정을 모두 거친 모델입니다(p5).

## 1-2 다음 토큰 예측과 생성 과정 (p6–7)

### 1-2 / [설명] p6

LLM은 답을 한 번에 꺼내지 않고, 토큰을 하나씩 골라 붙이며 문장을 만듭니다(p6).
지금까지의 글을 보고 다음에 올 토큰 후보들의 확률(나올 가능성)을 계산합니다(p6).
그중 하나를 골라 글 뒤에 붙이고, 이것을 되풀이해 단어, 문장, 답변이 완성됩니다(p6).
이 "조금씩 붙는 모습"은 뒤의 Streaming(스트리밍, 답을 조각으로 받는 방식) 실행에서 눈으로 봅니다(02_openai.py:61-74, 03_langchain.py:27-32).
확률을 어떻게 고르는지 조절하는 설정은 p19의 temperature와 top-p입니다(p19).

### 1-2 / [설명] p7

API(프로그램끼리 주고받는 창구)의 응답은 p6의 반복 생성을 서비스로 감싼 결과입니다(p7).
순서는 네 단계입니다: 요청 보내기 → 다음 토큰 후보 계산 → 토큰이 쌓여 답이 됨 → 종료 조건에서 응답 반환(p7).
1단계의 "메시지와 설정값"은 실습 코드의 `messages`와 `temperature`입니다(01_requests.py:32-35).
1단계의 "보낸다"는 `requests.post(...)` 한 줄이고, 4단계의 "반환"은 `new_response.json()`으로 받는 부분입니다(01_requests.py:45-49).
2·3단계는 서버 안에서 일어나므로 코드에는 보이지 않습니다(p7, 01_requests.py:45-49).

### 1-2 / [Q] 순서 맞추기 (p7)

**섞어서 보여 줄 항목**
- 선택된 토큰들이 누적되어 응답 메시지가 만들어진다.
- 사용자가 메시지와 설정값을 API 요청으로 보낸다.
- 생성이 종료 조건에 도달하면 최종 답변이 API 응답으로 반환된다.
- 서버의 모델이 입력 문맥을 읽고 다음 토큰 후보를 계산한다.

**정답 순서**: 요청 보내기 → 후보 계산 → 누적 → 반환 (p7).
**피드백**: p7의 1~4번 순서와 같습니다(p7). 코드에서 보이는 것은 1번과 4번뿐입니다(p7, 01_requests.py:45-49).

### 1-2 / [정리]

LLM은 토큰을 하나씩 예측해 붙이고, API는 그 과정을 "요청 → 계산 → 누적 → 반환" 네 단계로 감쌉니다(p6, p7).

## 2-1 토큰의 의미 (p8–9)

### 2-1 / [설명] p9

Tokenization(토큰화)은 사람의 말을 모델이 다룰 수 있는 작은 단위로 나누는 과정이고, 그 단위를 토큰이라고 합니다(p9).
토큰은 단어 하나와 늘 같지 않고, 단어 일부나 공백, 기호, 숫자 조각일 수 있습니다(p9).
한국어는 조사와 어미 때문에 더 잘게 나뉠 수 있습니다(p9).
p9 예시에서 "LangChain"은 "Lang"과 "Chain"으로, "만든다"는 "만든"과 "다"로 나뉩니다(p9).
입력한 질문과 모델의 답은 모두 토큰 단위로 셉니다(p9). 이 숫자가 다음 쪽의 비용과 이어집니다(p9, p10).

## 2-2 토큰 수와 비용 (p10–11)

### 2-2 / [설명] p10

LLM API의 비용과 처리량은 보통 입력 토큰 수와 출력 토큰 수로 정해집니다(p10).
입력 토큰에는 질문뿐 아니라 시스템 프롬프트(모델에게 주는 기본 지시)와 이전 대화도 모두 들어갑니다(p10).
출력 토큰은 모델이 새로 만든 답의 길이이고, 생각하는 과정이 있는 모델은 그 생각에 쓴 토큰도 들어갑니다(p10).
그래서 프롬프트와 답이 길수록 비용이 늘고 응답 시간도 길어집니다(p10).
실행 ①에서 찍은 응답 JSON 안에 `usage`가 있다면, 그것이 이 두 숫자를 보여 주는 자리입니다(p10, 01_requests.py:51-52, outline 어긋남 7).

### 2-2 / [되돌아보기] 실행 ①의 usage

- 다시 실행하지 않습니다(concepts 2-2). 위 실행 ① 단계 3의 출력으로 올라가 `usage`를 찾습니다(01_requests.py:51-52).
- 입력 토큰 수와 출력 토큰 수를 출력에서 직접 읽어 적습니다(p10).
- `usage`가 없으면 "이 환경에서는 제공되지 않음"이라고 적습니다(outline 어긋남 7).
- 입력은 질문 한 문장뿐인데도 토큰 수가 글자 수와 다른 이유를 p9와 연결해 봅니다(p9, 01_requests.py:33).

### 2-2 / [설명] p11

토큰 수를 줄이면 비용을 아낄 수 있습니다(p11).
필요한 정보만 골라 넣고, 반복되는 지시문과 대화 기록은 줄여 넣습니다(p11).
검색한 문서도 전부 넣지 말고 관련 있는 일부만 넣습니다(p11).
답의 형식과 길이를 분명히 정하면 불필요한 출력이 줄어듭니다(p11). 실습 질문의 "3문장으로"가 그 예입니다(p11, 01_requests.py:33).

### 2-2 / [Q] 객관식

**질문**: 입력 토큰 수에 들어가는 것을 모두 고른 것은? (p10)

| 보기 | 정답 | 피드백 |
|---|---|---|
| ① 사용자가 방금 입력한 질문만 | | 질문 말고도 모델이 답하는 데 쓰는 것이 모두 들어갑니다(p10). |
| ② 입력 프롬프트, 시스템 프롬프트, 이전 대화 내용 | ✔ | p10에 적힌 그대로입니다(p10). |
| ③ 모델이 새로 생성한 답변 | | 그것은 출력 토큰입니다(p10). |
| ④ API 키와 요청 주소 | | 이것은 전송에 쓰는 정보이고, p10의 입력 토큰 목록에는 없습니다(p10, 01_requests.py:16-19). |

### 2-2 / [정리]

비용은 입력 토큰과 출력 토큰으로 정해지고, 입력에는 시스템 프롬프트와 이전 대화까지 들어갑니다(p10).
토큰을 아끼려면 필요한 것만 넣고, 답의 형식과 길이를 정합니다(p11).

## 3-1 Context Window (p12–14)

### 3-1 / [설명] p14

Context Window(컨텍스트 윈도우)는 모델이 한 번의 요청에서 읽고 고려할 수 있는 토큰 범위입니다(p13, p14).
그 안에는 시스템 메시지, 사용자 메시지, 이전 대화, 도구 실행 결과가 모두 들어갑니다(p14).
모델은 이번 요청에 들어 있지 않은 정보를 직접 참조하지 못합니다(p14).
그래서 이전 대화를 기억하게 하려면 그 대화를 다음 요청에 다시 넣어야 합니다(p14). 실행 ②의 `context +=` 줄이 그 일을 합니다(p14, 02_openai.py:54-56).
긴 문서는 나눠서 필요한 부분만 찾아 넣고, 긴 대화는 요약하거나 중요한 상태만 따로 저장합니다(p14).

### 3-1 / [Q] 예측 후 실행 준비

**질문**: 첫 요청에서 "대한민국의 수도는 어디지?"라고 묻고, 두 번째 요청에서 "그곳의 인구는 어느정도야?"라고 묻습니다(02_openai.py:49, 56). 두 번째 요청에 이전 대화를 다시 넣지 않으면 모델이 "그곳"을 알아들을까요? (p14)

| 보기 | 정답 | 피드백 |
|---|---|---|
| ① 알아듣는다. 모델이 앞 대화를 기억한다 | | 모델은 이번 요청에 없는 정보를 직접 참조하지 못합니다(p14). |
| ② 알아듣지 못한다. 이전 대화가 이번 요청에 없기 때문이다 | ✔ | 맞습니다(p14). 실행 ②는 이전 대화를 다시 넣으므로 알아듣는지 확인합니다(02_openai.py:54-58). |

- 예측을 변수에 적어 두고, 실행 ② 단계 4의 [볼 지점]에서 비교합니다(concepts 3-1).

### 3-1 / [정리]

모델은 한 번의 요청에 들어 있는 토큰만 봅니다(p13, p14). 기억하게 하려면 이전 대화를 다시 넣어야 합니다(p14).

p14의 "이전 대화도 컨텍스트에 포함"을 코드로 한 것이 이 세 줄입니다(p14, 02_openai.py:55-57).
이전 대화를 다시 보내므로 두 번째 요청의 입력 토큰은 첫 요청보다 늘어납니다(p10, 02_openai.py:55-57).

### ② 단계 4 / [볼 지점]

- 두 번째 답이 서울의 인구를 말하는지 봅니다(02_openai.py:58). 그렇다면 "그곳"을 서울로 알아들은 것입니다(02_openai.py:56-58).
- 3-1에서 적은 예측과 비교합니다(concepts ▶ ② 단계 4). 알아들었다면, 이 코드가 이전 대화를 다시 넣었기 때문입니다(p14, 02_openai.py:55).
- 붙인 첫 답(`response_1.output`)은 글자가 아니라 여러 정보가 든 묶음이라 화면에 글자로 보이지 않습니다(outline 어긋남 2).

### ② 단계 5 / [설명] Streaming

`client.responses.stream(...)`은 답을 다 만든 뒤 한 번에 주지 않고, 만드는 대로 조각(이벤트)으로 보냅니다(02_openai.py:61-67).
이벤트 종류가 `output_text.delta`이면 그 안의 글자 조각을 줄바꿈 없이 바로 찍습니다(02_openai.py:71-72).
p6에서 본 "토큰을 하나씩 골라 붙인다"를 화면에서 보는 단계입니다(p6).
마지막에 `Counter`(개수를 세는 도구)로 어떤 종류의 이벤트가 몇 번 왔는지 셉니다(02_openai.py:68-70, 74).

### ② 단계 5 / [볼 지점]

- 답 글자가 한 번에 뜨지 않고 조금씩 이어지는지 봅니다(02_openai.py:72, p6).
- 맨 아래 `Counter(...)`에서 이름에 `output_text.delta`가 들어간 항목이 몇 번인지 출력에서 직접 읽습니다(02_openai.py:71, 74).
- 이 숫자는 조각 수입니다(02_openai.py:72). 출력 토큰 수와 같다고 보지 않습니다(outline 어긋남 6).

### ② / [정리]

Single Turn은 문자열 하나를, Multi Turn은 역할이 붙은 메시지 목록을 보냅니다(02_openai.py:36-39, 47-51).
이전 답을 `context`에 다시 넣어야 "그곳"을 알아듣고(p14, 02_openai.py:55), Streaming은 답이 조각으로 쌓이는 모습을 보여 줍니다(p6, 02_openai.py:64-72).

## 3-2 입력 품질과 출력 품질 (p15–16)

### 3-2 / [설명] p16

LLM의 답 품질은 모델 성능뿐 아니라 컨텍스트에 어떤 정보가 들어갔는지에 크게 좌우됩니다(p15, p16).
목표가 분명하면 답의 방향이 안정되고, 배경 정보가 충분하면 추측과 환각(사실이 아닌 내용을 지어내는 것)이 줄어듭니다(p16).
반대로 불필요하거나 서로 부딪치는 정보가 많으면 판단이 흐려질 수 있습니다(p16).
좋은 프롬프트는 답을 맞히라고 요구하지 않고, 답을 만들 수 있는 조건을 줍니다(p16).
실행 ②의 시스템 지시 "경어체, 단답형"은 출력 형식을 알려 준 예입니다(p16, 02_openai.py:48).

### 3-2 / [체크] p16의 4항목

- [ ] 역할과 목표를 분명히 준다(p16).
- [ ] 필요한 배경 정보와 제약 조건을 함께 준다(p16).
- [ ] 원하는 출력 형식과 평가 기준을 알려 준다(p16).
- [ ] 모호한 지시나 서로 충돌하는 요구를 줄인다(p16).

이 4항목을 5절의 CodeMate 지시문 틀로 다시 씁니다(outline 3-2).

### 3-2 / [정리]

답의 품질은 컨텍스트에 넣은 정보가 크게 좌우하고, 좋은 입력은 역할·목표, 배경·제약, 출력 형식, 모호함 줄이기를 갖춥니다(p16).

## 4-1 System, User, Assistant 역할 (p17–18)

### 4-1 / [설명] p18

Chat 기반 LLM API는 대화를 역할이 붙은 메시지 목록으로 표현합니다(p18).
System 메시지는 모델의 역할, 규칙, 제약 조건을 정하고, User 메시지는 질문과 요청과 입력 데이터를 전합니다(p18).
Assistant 메시지는 LLM이 만든 답이며, 다음 요청에 다시 넣어 맥락을 이어 줍니다(p18).
역할 구분은 모양만의 문제가 아니라, 모델이 지시의 우선순위와 대화 흐름을 읽는 기준입니다(p18).
실행 ②의 `context`가 바로 이 목록이고, 실행 ③에서는 `SystemMessage`와 `HumanMessage`로 같은 구분을 합니다(02_openai.py:47-50, 03_langchain.py:17-21).

- 다시 실행하지 않습니다(concepts 4-1). 위 ② 단계 3의 코드 화면으로 올라갑니다(02_openai.py:47-50).
- p18의 System 자리에 코드는 `developer`를 씁니다(02_openai.py:48). 주석에 "developer: 시스템 지시"라고 적혀 있습니다(02_openai.py:46, p18, outline 어긋남 1).
- p18의 Assistant 메시지는 `response_1.output`을 붙이는 줄에 해당하지만, 화면에 글자로 보이지는 않습니다(02_openai.py:55, outline 어긋남 2).
- 01은 `user` 역할 하나만 씁니다(01_requests.py:33).

### 4-1 / [Q] 객관식

**질문**: 모델이 지켜야 할 규칙과 제약 조건은 어느 역할의 메시지에 넣나요? (p18)

### 4-1 / [정리]

System은 규칙, User는 요청, Assistant는 모델의 답이며, 이 구분이 지시의 우선순위와 대화 흐름을 정합니다(p18).

## 4-2 모델 파라미터의 영향 (p19)

### 4-2 / [설명] p19

모델 파라미터(모델에 함께 보내는 설정값)는 같은 입력에 대해 답이 얼마나 다양하고 예측 가능할지를 조정합니다(p19).
Temperature는 다음 토큰들의 확률을 조정하고, Top-p는 후보 토큰들의 누적 확률 한도를 조정합니다(p19).
둘 다 낮으면 일관되고 보수적인 답에, 높으면 다양한 표현과 아이디어에 유리합니다(p19).
너무 높으면 가능성이 거의 없는 토큰이 나올 수 있어 주의합니다(p19).
p6에서 "후보 중 하나를 고른다"고 했는데, 이 고르는 방식을 바꾸는 값이 이 두 설정입니다(p6, p19).

### 4-2 / [지도] 실행하지 않고 코드만 보기

- 01의 `"temperature": 0.5`는 요청 본문에 실제로 들어가 전송됩니다(01_requests.py:35).
- 모델이 `gpt-6-luna`일 때만 temperature를 빼고, 사내 경로에서는 0.5가 그대로 전송됩니다(01_requests.py:38-42, outline 어긋남 3).
- 02 끝의 `temperature=0.2`, `top_p=0.1` 예시는 `"""` 안에 있어 실행되지 않습니다(02_openai.py:81-89).
- 02의 주석은 temperature와 top_p를 함께 조정하는 것을 권장하지 않는다고 적습니다(02_openai.py:79).

### 4-2 / [Q] 객관식

**질문**: 코드 생성에 알맞은 조합은? (p19 표)

| 보기 | 정답 | 피드백 |
|---|---|---|
| ① 낮은 temperature / 낮은 top-p | ✔ | p19 표에서 사실 기반 답변, 코드 생성, 요약에 알맞다고 합니다(p19). |
| ② 낮은 temperature / 높은 top-p | | p19 표에서는 업무 문서, 설명문에 알맞습니다(p19). |
| ③ 높은 temperature / 낮은 top-p | | p19 표에서는 가벼운 문장 변형에 알맞습니다(p19). |
| ④ 높은 temperature / 높은 top-p | | p19 표에서는 아이디어 발산, 브레인스토밍에 알맞습니다(p19). |

### 4-2 / [정리]

Temperature와 Top-p는 다음 토큰을 고르는 방식을 바꾸며, 낮으면 일관되고 높으면 다양합니다(p19).
실습 코드에서 실제로 전송되는 값은 01의 `temperature: 0.5`뿐이고(모델이 `gpt-6-luna`이면 빠짐), 02의 예시는 참고용입니다(01_requests.py:35, 40-42, 02_openai.py:81-89).

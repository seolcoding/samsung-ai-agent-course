# 강사용 진행·검토 기준

4일치 학습자 정본은 `lessons/day01.ipynb`~`day04.ipynb`다. 진행 시간은 [INSTRUCTOR_TIMING.md](INSTRUCTOR_TIMING.md)의 13개 블록·하루 480분을 따른다. 세부 배분은 운영안이며 현장 진행에 따라 조절한다. 학습자 본문에는 분·시각을 표시하지 않는다.

## 시작과 운영

1. `uv sync --extra notebooks` 후 VS Code에서 프로젝트 `.venv` 커널을 선택한다.
2. 각 일차 첫 셀은 `RUN_LIVE=False`, `ENABLE_LANGFUSE=False`로 시작한다. 본문을 읽고 위에서부터 실행한다.
3. 설명·그림 → 결과 예상 → 코드 실행 → CodeMate 지시 → 결과 검토 → 재지시 순서로 진행한다.
4. 기본 실습에서 확인한 것은 실행 계약이다. 실제 모델·사내 API·CodeMate UI의 품질과 연결은 해당 환경에서 확인한다.
5. 수강생이 먼저 완료하면 해당 CodeMate 과제의 오류·경계 입력을 확장하거나 캡스톤 주제를 정리하게 한다.

### 11차수 피드백을 반영한 진행 원칙

근거는 [11차수 수강생 피드백](2026_11차수_수강생피드백.md)이다. 설문에서는 실습을 늘려 달라는 요청이, 운영 측에서는 개념의 "왜"를 더 설명해 달라는 요청이 나왔다. 이 과정에서는 둘을 CodeMate 실습으로 묶는다. 코드 작성은 CodeMate에 맡기고, 강사는 개념의 이유와 코드 리뷰에 시간을 쓴다.

1. **과정 소개와 캡스톤 예고.** 1일차와 3일차 시작 때 강사 소개 다음에 과정 커리큘럼 전체를 소개한다(30분 이내). 컨플루언스 "2. 커리큘럼" 페이지에서 언제든 볼 수 있다고 알린다. 3일차에는 이전 차수 캡스톤 우수사례를 보여 주며 캡스톤을 예고하고, 주제를 미리 생각하게 한다. 이 시간은 아직 [시간표](INSTRUCTOR_TIMING.md)에 따로 잡혀 있지 않다.
2. **코드를 배우는 이유.** 1.1에서 "코딩은 AI가 해도 왜 코드를 보는가"를 먼저 말한다. 설계는 사람이 한다. 코드를 알면 API 오류나 할루시네이션의 원인을 빨리 찾는다. 코드 구조를 알고 지시하면 결과가 좋고 엉뚱한 재시도로 버리는 토큰이 준다.
3. **개념은 "정의 → 왜 중요한가 → 어디에 연결되는가" 순서로 설명한다.** 함수 기능보다 역할·쓰는 이유·쓰는 시점을 말한다.
   - 1.2.2 Context Window: 한 번의 요청에서 읽을 수 있는 토큰 범위다. 모델은 매번 대화를 통째로 다시 읽는다. 넘치면 앞부분을 잃고 할루시네이션이 생길 수 있고, 길수록 매 턴 비용이 커진다. 그래서 요약(compaction), RAG(2.1), LangGraph의 state 설계(2.2)가 필요하다.
   - 1.3.2 Tool Calling: 도구를 만들고 등록하는 방법보다, 모델이 도구를 어떻게 고르는지와 호출이 어떻게 반복되는지를 구조로 설명한다.
4. **선행 학습 위치 안내.** 실습을 시작할 때 "이 내용은 O일차 X 블록에서 다뤘다"고 알려 준다. 교재에 없다고 느끼는 내용은 대부분 앞 일차에서 한 번 이상 다룬 것이다.
5. **화면 크기.** 코드와 Langfuse 화면은 뒷자리에서도 읽히도록 확대해서 보여 준다.
6. **환경 셋팅.** 강의장 PC 기준으로 설치한다(약 1.5~2시간). 시작 전에 셋팅을 직접 하는 목적(업무 복귀 후 같은 순서로 설치)을 말하고, 막히면 손을 들게 한다. 업무 PC용 가이드는 따로 제공하지 않는다.

## 주제별 기대 답변과 확인 기준

아래는 CodeMate 과제의 단일 정답 코드가 아니라 검토 기준이다. 수강생이 다른 구현을 제시해도 입출력·실패·승인·근거 조건을 실제 실행으로 만족하면 인정한다. 실행 예시의 공통 구현은 `src/courseware/`, 수정 전 기준은 Git 커밋에 있다.

### 1.1.1 AI·머신러닝·LLM은 어떤 관계인가

입력은 temperature, 모델은 12와 -100 및 선형 관계, 출력은 판매량 예측이다. 학습 범위 밖 외삽은 실제 현상을 보장하지 않는다. LLM 설명에서도 다음 토큰 생성과 사실 검증을 구별한다.

### 1.1.2 답변에서 도구 사용으로 확장하기

실패는 실제 도구 호출 전에 검출된다. 도구 이름 검사와 인자 검사는 다른 책임이다. get_weather 자체의 지원 지역 검사는 값의 허용 범위를 확인한다.

### 1.1.3 판단·실행·관찰과 종료 조건

기본 실행은 tool→answer, 한도 1은 tool 이후 stopped다. 오류를 조용히 삼키기보다 명시적 오류 상태와 실행 기록을 남겨야 한다.

### 1.1.4 VS Code·커널·환경변수 준비

패키지 오류는 커널 선택부터 확인한다. CodeMate 실제 UI는 현장 검증 대상이다. 비밀값을 노트북 출력·프롬프트·커밋에 넣지 않는다.

### 1.1.5 Agent의 네 가지 책임 설명하기

제안 생성 위치를 실제 모델 호출로 바꾼다. 실행 경계와 반복 제어는 모델 밖에 유지한다.

### 1.2.1 학습과 생성, 다음 토큰의 의미

샘플링 원리를 보여 주며, 모델의 실제 토큰화나 확률을 재현하지 않는다. 실제 API에서 temperature=0도 모든 실행의 동일성을 보장한다고 설명하지 않는다.

### 1.2.2 토큰과 컨텍스트를 관리하기

개수 예산은 원리용 모형이다. 실제 운영에서는 토큰화와 출력 한도를 고려하고, 중요한 구조적 상태를 자연어 요약에만 맡기지 않는다.

### 1.2.3 역할이 붙은 메시지와 요청·응답

raise_for_status로 HTTP 오류를 정상 응답 파싱 전에 검출한다. 401은 인증, 429는 한도/빈도, 5xx는 서버 측 문제의 단서이며 실제 원인은 서버 응답과 환경을 확인한다.

### 1.2.4 대화 유지와 스트리밍

최종 assistant 메시지는 조각을 합친 뒤 추가한다. 사용자별 세션 경계를 검증하고 중간 실패를 구분한다.

### 1.2.5 직접 호출과 공통 모델 설정

provider 선택과 모델 기능 호환성을 분리한다. 예외를 숨기는 자동 fallback은 쓰지 않는다. 실제 연결의 모델명과 키는 환경변수로 관리한다.

### 1.3.1 Runnable과 LCEL의 입출력

정규화 노드는 dict를 받아 dict를 반환해야 prompt가 topic 키를 찾을 수 있다. 단순 문자열을 반환하면 계약이 깨진다.

### 1.3.2 도구 스키마와 실제 Agent 실행

스키마만 읽고 안전하다고 판단하지 않는다. 실제 invoke에서 범위와 타입이 검사되는지 확인한다. 문자열 숫자의 자동 변환 허용 여부도 명시해야 한다.

### 1.3.3 구조화 출력과 사실 검증

구문·스키마·근거 검사는 서로 다르다. 형식이 맞는 허구의 출처를 별도 대조로 잡는 것이 핵심이다.

### 1.3.4 대화 기억과 세션 경계

세션 A만 4개 메시지로 늘고 B는 2개다. 사용자 ID와 세션 ID는 목적에 맞게 구분하며, 필수 상태를 요약에서 잃지 않도록 구조화한다.

### 1.3.5 첫 Agent를 CodeMate와 검토하기

도구 호출 기록으로 42의 출처를 확인한다. 모의 모델은 multiply 전용이므로 도구 추가 실습의 선택 능력을 검증하려면 모델 대역도 명시적으로 확장하거나 실제 모델 경로를 사용해야 한다.

### 2.1.1 모델에 지식을 넣는 두 가지 위치

RAG는 입력 맥락을 바꾸고 Fine-Tuning은 모델 매개변수를 학습한다. D1을 검색하는 것과 그 근거로 답변의 모든 주장을 뒷받침하는 것은 별도다.

### 2.1.2 Loading·Splitting·Embedding

청크 수가 적거나 많다는 이유만으로 좋고 나쁨을 판단하지 않는다. 질문에 필요한 조건이 함께 검색되는지 평가한다. 문서와 질문의 임베딩은 같은 설정을 쓴다.

### 2.1.3 Storage·Retrieval·Generation

Chroma 연결과 검색은 실제 동작한다. 모의 임베딩 한계를 밝히고 상위 후보가 있다는 이유만으로 답을 생성하지 않는다. 운영용 임계값은 실제 질의셋으로 정해야 한다.

### 2.1.4 사내 RAGaaS와 사외 모의 응답

모의 RAGaaS는 인증·색인·실검색을 검증하지 않는다. 사내 경로는 원본 실습과 같은 요청(`rp-aicoa-meritz-pet` 인덱스, `rag-public` 권한)을 보낸다. 키 값은 읽어 설명하지 않는다.

### 2.1.5 근거 없는 질문과 검색 평가

검색 recall과 답변 faithfulness는 다른 평가다. 기대 문서를 넓게 포함시키는 전략만으로 좋은 RAG가 되지 않는다.

### 2.2.1 선형 체인에서 상태가 있는 그래프로

노드가 State의 일부를 반환하고 그래프가 합친다. 상태를 전역변수로 관리하지 않아도 된다.

### 2.2.2 Node·Edge·State와 Reducer

add Reducer가 있으면 노드가 신규 항목만 반환해야 누적 중복이 생기지 않는다. Reducer는 데이터 병합 규칙이며 노드 실행 순서를 대신 정하지 않는다.

### 2.2.3 도구 호출 뒤 모델로 돌아오기

모의 모델에서 도구가 없으면 추가 입력 안내로 종료한다. 순환 Edge와 도구 호출 여부 조건이 함께 필요하다.

### 2.2.4 사람의 승인으로 멈추고 재개하기

중단한 노드는 재개 때 재실행될 수 있다. 승인 결과를 확인한 별도 실행 노드에 부작용을 배치한다. 거절 메시지보다 실제 상태와 실행 기록을 확인한다.

### 2.2.5 분기를 바꿨으면 양쪽을 실행하기

승인 전 근거 검사 분기를 추가한다. 기존 정상·거절 검증을 유지하면서 새 no-evidence 경로를 검사한다.

### 2.3.1 언제 역할을 나눌까

곱셈에는 역할 분리의 이득이 작다. 보고서는 근거 수집과 서술·검토의 계약을 나누는 이득이 있지만 전달 오류와 비용을 측정해야 한다.

### 2.3.2 Researcher·Writer·Supervisor의 계약

본문·ID·출처를 함께 전달한다. 고정 Workflow를 자율 Supervisor라고 부르지 않는다. 근거 없음 분기와 승인 경계는 4일차로 연결한다.

### 2.3.3 Streamlit의 재실행과 세션 상태

session_state는 브라우저 세션의 재실행 사이 상태를 유지하며 영구 저장소와 다르다. API 호출은 새 입력 이벤트 안에 둔다.

### 2.3.4 질문·답변·근거를 한 화면으로 연결하기

k 값을 UI에서 받아 검색 함수로 전달하는 계약이 필요하다. UI 범위 검사와 서버/함수 쪽 검사 모두 생각한다. 재실행 때 이전 대화가 소실되지 않아야 한다.

### 2.3.5 하나의 실행을 끝까지 설명하기

목표와 검증 사례를 먼저 정한 후 최소 변경을 수행한다. 원본 데모의 기능 수보다 흐름과 실패 경로를 설명하는 능력을 확인한다.

### 3.1.1 M1의 구성요소를 한 경로로 읽기

검색 후보와 반환 답변은 확인할 수 있지만 모델의 실제 추론이나 의미적 사실성은 이 기록만으로 보장할 수 없다.

### 3.1.2 M2 패키지와 실행 명령 확인

pyproject는 의존성 범위, uv.lock은 재현할 구체 버전이다. SDK 0.x 코드를 1.x에서 그대로 실행하지 않는다.

### 3.1.3 Client·Server의 요청과 응답

ASGI 검증은 앱의 라우팅·응답 계약을 확인한다. DNS·프록시·TLS·방화벽·사내 인증은 별도의 환경 검증이다.

### 3.1.4 연결 실패를 단계별로 좁히기

목록 발견과 실제 실행은 다른 권한·입력·처리 경로를 거칠 수 있다. 가장 작은 실패 요청으로 원인을 좁힌다.

### 3.2.1 Host·Client·Server의 책임

현재 노트북이 Host 역할, Client 객체가 연결, build_mcp 결과가 Server다. 도구 구현과 Host의 모델 선택을 분리한다.

### 3.2.2 Tools·Resources·Prompts 실행하기

기능 성격에 따라 Tool·Resource를 선택한다. 에러·빈 결과·정상 응답의 계약을 명시하고, 실제 원문 범위를 제한한다.

### 3.2.3 stdio와 get_tools로 LangChain에 연결하기

서버: uv run python -m courseware.mcp_server, URL http://127.0.0.1:8765/mcp, 어댑터 transport는 http. stdio는 Client가 프로세스를 시작하므로 별도 서버 실행이 필요 없다.

### 3.2.4 도구 수정과 계약 검토

범위 검사가 서버 함수에 있으므로 호출 시 실패한다. 스키마에 Field ge/le를 추가하면 발견 단계에도 범위가 보인다. 정상 빈 목록과 예외는 구별한다.

### 3.3.1 MCP와 A2A의 책임 경계

MCP는 기능 접근, A2A는 Agent 간 작업 계약이다. Task와 Artifact는 장기 작업/산출물 관리에 유용하며 모든 응답이 반드시 Task일 필요는 없다.

### 3.3.2 Agent Card와 서버 경로 확인

Card 조회는 성공할 수 있으나 선언된 실행 URL로 전송하면 실패한다. Card의 지원 프로토콜·주소·기능을 먼저 읽는다.

### 3.3.3 Message를 보내고 응답 읽기

출처 표시는 근거 위치를 제공한다. 내용과 실제 근거 일치 여부는 추가 검토가 필요하다. SDK 경고를 지우기 위해 예외 전체를 숨기지 않는다.

### 3.3.4 Researcher에 맡길 범위를 정하기

역할 분리는 지시문뿐 아니라 입출력·다음 단계 조건으로 검증한다. 없는 주제에 답변을 거절하는 경로가 필요하다.

### 3.4.1 Subgraph의 입출력 경계

어댑터가 topic→query, evidence→sources로 경계를 명시한다. 디버그 필드를 외부 계약에 포함할 필요는 없다.

### 3.4.2 Checkpointer와 Store

thread는 대화 상태, user namespace는 공유 데이터 범위다. namespace는 접근제어 그 자체가 아니며 인증된 사용자와 서버에서 연결해야 한다.

### 3.4.3 Send로 여러 Worker에 배분하기

리스트 병합은 결과를 누적하지만 정렬이나 중복 제거는 수행하지 않는다. 독립 작업을 배분하고 합치는 계약을 따로 정한다.

### 3.4.4 반복 실행·중복·실패를 다루기

재시도의 대상과 중복 처리 기준을 먼저 정한다. 리스트 Reducer만으로 정확히 한 번 실행이나 중복 제거가 보장되지는 않는다.

### 3.4.5 경계별 검토로 정리하기

검증 범위를 과장하지 않는 것이 핵심이다. ASGI·stdio 성공과 사내 네트워크 성공을 구분한다.

### 4.1.1 모델 밖의 실행 환경 설계

종료는 성공뿐 아니라 예산 소진·진전 없음·근거 부족도 포함한다. 재시도 자체가 품질 개선을 보장하지 않는다.

### 4.1.2 Workflow와 Agent를 선택하는 기준

스키마에 맞는 제안이어도 실행 권한이 생기지는 않는다. 필수 승인과 부작용 경계는 프로그램에서 집행한다.

### 4.1.3 SKILL.md를 실행 가능한 작업 규칙으로 읽기

Skill은 작업 맥락을 전달한다. 출처 ID 존재·필수 소제목은 코드로 검사하고 내용의 근거 충실성은 사람이 문서와 대조한다.

### 4.1.4 DeepAgents와 파일 작업 범위

기본 모드에서는 프레임워크와 파일 접근 경로만 검증한다. 실제 모델의 Skill 사용·계획 품질은 호출 기록과 산출물을 따로 검토한다.

### 4.1.5 작업 지시와 검증 루프 연결

작은 변경→실행→관찰→재지시의 루프를 만든다. 무엇이 통과해야 완료인지 수정 전에 합의한다.

### 4.2.1 Trace·Span·Callback·observe

추적은 실행 사실을 확인한다. 성공한 HTTP 호출이나 오류 없는 Trace만으로 답변 품질을 보장하지 않는다.

### 4.2.2 규칙 평가와 LLM-as-a-Judge

형식 1.0·유효 출처 True는 의미적 정확도 100%가 아니다. 실제 Judge 점수도 사람 검토 없이 정답으로 사용하지 않는다.

### 4.2.3 실행을 기록하고 Langfuse에 연결하기

지역별 BASE_URL과 같은 프로젝트 키를 짝으로 확인한다. SDK 호출·flush·대시보드 저장 확인은 각각 다른 증거다. 실제 모델 비용이 아닌 Fake 모델임을 표시한다.

### 4.2.4 사례에서 설계 원칙 가져오기

사례의 사실·수업 적용·검증되지 않은 효과를 분리한다. 특정 제품 도입이 품질을 자동 보장한다고 설명하지 않는다.

### 4.2.5 한 문제를 골라 개선하기

수정한 경계에 맞는 회귀 사례를 재실행한다. 단순 점수 상승만으로 내용 품질이 좋아졌다고 말하지 않는다.

### 4.3.1 완료 기준부터 정하기

자유 주제도 성공·거절·근거 없음·오류의 기준을 먼저 갖춘다. 실제 회사 정책이나 자료라고 주장하지 않는다.

### 4.3.2 Supervisor와 작업자의 계약

라우팅을 Pydantic으로 제한하고 실제 실행 제약은 프로그램에서 확인한다. 연구·승인·작성·평가 후 FINISH에 도달한다.

### 4.3.3 작은 경로부터 실행하고 화면 연결하기

처음부터 모든 외부 서비스로 바꾸지 않는다. 작은 변경에도 승인·거절·근거 없음의 계약이 유지되는지 실행한다.

### 4.3.4 보고서 품질과 승인 화면 검증

UI의 클릭 경로와 그래프의 의미가 일치해야 한다. 콘텐츠 품질 검토는 출처 ID 검사와 별개이며 실제 모델 전환 뒤 다시 수행한다.

### 4.3.5 시연과 동료 검토

피드백은 재현 입력·관찰 결과·기대 결과를 포함한다. 실제로 보지 않은 사내 동작이나 모델 품질을 완료 항목에 넣지 않는다.

### 4.3.6 실행과 인수인계 정리

누군가 같은 환경에서 실행할 수 있는 안내가 최종 산출물이다. 작업 기록과 검증 범위를 함께 전달한다.

## 사내 전환 리허설

환경 파일을 선택하고 키 값은 표시하지 않는다. LLM 텍스트 응답→도구 호출→구조화 출력→임베딩→RAGaaS 인증·응답 구조→Langfuse 대시보드 기록 순서로 작은 요청을 확인한다. 실패한 단계는 실패로 남기고 mock으로 자동 전환하지 않는다. 현재 노트북의 `.env` 로드는 기본 파일이며 다른 환경은 실행 시 변수 주입 또는 명시적 경로 수정으로 선택한다.

학생 PC 설치와 CodeMate 화면·기능, 사내 문서 접근 정책, 컨플루언스 최신 과제는 현장에서 최종 확인한다. 현재 검증 증거는 [VALIDATION.md](VALIDATION.md)를 따른다.
